# Stack 08: Testing & Code Quality

## Tools

| Tool | Purpose | Command |
|---|---|---|
| TypeScript strict | Catch type errors | `npm run typecheck` → `next typegen && tsc --noEmit` (typegen creates the global `PageProps`/`LayoutProps`/`RouteContext` types) |
| ESLint (Next.js flat config) | Lint + React/Next rules | `npm run lint` → `eslint` |
| Vitest | Unit and property tests | `npm test` → `vitest run` |
| Vitest coverage (v8) | Coverage report for `lib/` | `npm run test:coverage` |
| tsx | Run TS scripts (seed, evals) | `npx tsx scripts/<name>.ts` |

All scripts are listed in the [README](../../README.md#getting-started) and `package.json`. `npm run check` runs lint + typecheck + data validation + tests and must pass locally before every push. CI runs these plus the build and the packing eval (Stack 09).

> Lint: Next.js 16 removed `next lint`. The project uses the ESLint flat config (`eslint.config.mjs`) generated by `create-next-app`.
> Vitest config is `vitest.config.mts`. It aliases `server-only` to a no-op so server modules can be unit-tested in plain Node.

## Conventions

- Branch names, if a branch is used: `feat/<short>`, `fix/<short>`, `docs/<short>`, `eval/<short>`.
- Commit messages: imperative, scoped, e.g. `engine: enforce support ratio in validator`.
- Commit/PR description: what changed, how it was tested, screenshots for UI, and eval before/after numbers for prompt or engine changes.
- **Workflow (`docs/decisions.md`, 2026-10-21):** agents worked in git worktrees, work was merged locally, and the local CI gate (`agent-ship ci`: secret scan, floor guard, lint, typecheck, tests, build, packing eval) had to pass before pushing straight to `main`. GitHub Actions CI then re-ran, and a red CI was the stop signal. There was no per-PR review and no branch protection.
- Code comments explain *why* (e.g. why fragile items go last), not *what*.
- Keep engine code plain and grouped by the rule it enforces. `validateLayout` checks each rule of the rule table (Stack 03 §3) and reports a violation code per broken rule, which makes a layout easy to walk through.

## Decision log

Keep `docs/decisions.md`: one line per decision with the date, the decision, the reason, and the alternatives considered. Examples: margin = 15% (from eval), `minSupport` = 0.7 (assumption), TypeScript over Python (Vercel). The brief asks us to justify tool and technical choices, and this file is the evidence.
